Product Requirements Document

React Native (TypeScript) frontend · Spring Boot 4.1 / Java 25 backend · PostgreSQL

1. Overview

Cartculate is a smart, playful grocery and recipe-scaling app that lets a household manage a shared shopping list across multiple stores, with dynamic pricing, recipe-driven ingredient aggregation, pantry-stock awareness, and spending analytics.

1.1 Problem statement

Grocery shopping across multiple stores with a mix of recipe-driven needs and standalone items is hard to track by hand: prices vary by store, the same ingredient shows up across multiple recipes, and what's already stocked at home versus what actually needs buying gets lost between a paper list and a shopping trip.

1.2 Goals

  • Consolidate ingredient needs across recipes and manual entries into one store-sectioned shopping list.
  • Track per-store, per-item pricing so the user always sees an accurate running cost.
  • Let the user account for pantry stock already on hand, so the "need to buy" quantity is accurate, not just the recipe-required total.
  • Support a lightweight in-store checkout flow (checking items off) and reconcile the trip against the actual receipt total afterward.
  • Surface spending patterns over time (by store, by category, by item price trend).

1.3 Non-goals (current scope)

  • Multi-user / multi-household support. The system currently assumes a single seeded user (CURRENT_USER_ID); no authentication exists yet.
  • Real-time collaborative editing of a shared cart.
  • Payment or checkout integration with any store.

2. Personas

Primary persona — "The Household Shopper": Plans meals via recipes, shops at 2+ stores for better prices, wants to know what's already at home before buying more, and wants an accurate running total while shopping.

3. Functional Requirements

Feature 1 — The Unified Shopping Cart (Main Screen)

● Implemented
  • Items are grouped by store section (e.g. Puregold, S&R).
  • Consolidated Ingredient Aggregation: if the same item is needed by multiple recipes (and/or added manually), the cart shows one consolidated line with a combined quantity.
  • Expandable breakdown (accordion): tapping a consolidated item (when it has more than one source) expands a breakdown showing how much came from each recipe, plus an "Others" bucket for manually-added quantity.
  • + / − controls: manual taps always adjust the item's "Others" bucket for that store; recipe-sourced quantity is only changed by editing the recipe's scale factor.
  • Per-store pricing: the same item can have a different price at each store (Store_Price), and the displayed running total reflects quantity × store price per item, summed across the active cart.
  • Quantity-zero items are excluded from the active total but remain visible in a separate "Cart excluded" section at the bottom (they're not deleted, just inactive for the current trip).

Feature 2 — Smart Recipe Tab

● Implemented
  • Users can view saved recipes, each showing its base ingredient list.
  • Scale factor: each recipe card has a scale selector (×0.5 / ×1 / ×2) that multiplies every ingredient's quantity.
  • Add to cart: pushes the scaled ingredients into the cart, tagged with that recipe as the source (drives the accordion breakdown on the Cart screen).
  • Store routing per ingredient: an ingredient can have an explicit target store; if none is set, the system defaults to whichever store has the lowest known price for that item.
  • Recipe creation: "+ New recipe" opens a form (name, dynamic ingredient rows with an item picker, quantity, and unit dropdown) that calls POST /api/users/{userId}/recipes.
The creation form doesn't yet expose per-ingredient store routing — new recipes default to the cheapest-price-store fallback, even though the backend supports explicit routing via targetStoreId.

Feature 3 — Smart Insights & Statistics Tab

● Implemented
  • Monthly budget tracking: a progress bar comparing spend-to-date against a budget limit for the current month.
  • Store-by-store comparison: a bar chart of total spend per store.
  • Spending by category: a pie chart breaking down spend by item category (Vegetables, Meat, Toiletries, etc.), derived by flattening every archived receipt's item manifest.
  • Price trend: a line chart tracking one item's price over time.
Known limitation: trends the item's price across all stores it appeared at, not one specific store — the receipt manifest schema records storeId at the receipt level, not per line item.

Feature 4 — AI-Powered Receipt Scanner

◐ Partial
  • Capture: user takes a photo or uploads a receipt image.
  • Review screen: shows each parsed line next to its matched master item, with a "matched" or "needs review" badge; ambiguous matches offer a dropdown of alternative matches.
  • Confirm: on confirm, the reviewed items are archived as a purchase and their prices upsert into Store_Prices.
Not yet implemented: the actual OCR + LLM matching call — POST /api/receipts/scan currently returns a hardcoded mock response, pending a decision on which vision/LLM provider to integrate. The "Confirm" step, however, calls the real backend endpoints.

Feature 5 — Home Mode / Away Mode & Pantry Overrides

● Implemented
  • A persisted (server-side) toggle between Home Mode and Away Mode on the Cart screen.
  • Home Mode: each item shows a secondary "already have" stepper (pantry override). The displayed "need to buy" quantity is totalQuantity − pantryOverrideQty, floored at zero. An optional free-text/emoji reason (e.g. "Freezer Find") can be attached.
  • Away Mode: each item instead shows a checkbox for checking it off mid-trip.
  • Master Reset: a destructive action (with a confirmation prompt) that clears every checkbox across the whole cart without touching quantities or pantry overrides — an "abandon this trip's checkout progress" escape hatch, distinct from the per-store reconciliation flow below.
  • Items split across multiple recipe sources (e.g. Carrots needed by both Caldereta and Giniling) get independent pantry-override/checkout controls per source, shown inside the accordion breakdown rather than one shared control for the whole consolidated item.

Feature 6 — Trip Conclusion & Auto-Reconciliation

● Implemented
  • From Away Mode, once a store section has at least one checked-off item, a "Done Checkout" button appears for that store.
  • Tapping it opens a reconciliation screen showing the checked-off items and their expected cost, an input for the actual receipt total, and a price variance alert if they differ beyond a rounding tolerance.
  • Confirm archives the trip as one receipt-level Purchase_History row (with a JSON item manifest) and resets the checked-off items' quantities to zero, clearing their checkboxes.
  • Per product decision: a price variance is logged as part of the receipt total but does not automatically redistribute across individual item prices in Store_Prices — those still only get updated via the Receipt Scanner or manual entry.

4. Data Model Summary

See the Data Model page for the full ER diagram. Key entities: User (with a persisted Home/Away mode), Item (master catalog with category), Store, Store_Price (per item-store price), Recipe / Recipe_Ingredient, User_Cart_Item (the active cart, with pantry-override and checkout-checkbox state), and Purchase_History (receipt-level, with a JSON item manifest).

5. Non-Functional Notes

  • Decimal precision: quantities and prices are stored as NUMERIC(10,2) or NUMERIC(10,3) depending on the field. On the frontend, src/utils/inputSanitization.ts enforces this at input time — free-text quantity/currency fields (reconciliation's actual receipt total, new-recipe ingredient quantities) are sanitized as-you-type via regex, capping decimals at 2 places, and every currency display goes through a shared formatCurrency() helper for consistent formatting.
  • Schema evolution: the backend uses Hibernate's ddl-auto=update, which can only add schema — it cannot safely add a NOT NULL column to a table that already has rows. See ADR-004 for the operational implication.
  • Auth: none yet. CURRENT_USER_ID is hardcoded on the frontend pending a real login/session system.
