C4 Architecture Diagrams

Three levels of the C4 model: System Context, Container, and Component (backend only).

1. System Context

Who uses Cartculate, and what it talks to.

C4Context
    title Cartculate — System Context

    Person(shopper, "Household Shopper", "Plans meals via recipes, shops across multiple stores, tracks spend")

    System(cartculate, "Cartculate", "Consolidates shopping lists across stores, tracks pricing, pantry stock, and spend")

    System_Ext(visionLlm, "Vision/LLM Provider", "Planned: OCR + item matching for scanned receipts. Not yet integrated.")

    Rel(shopper, cartculate, "Manages cart, recipes, checks out, reviews spending", "Mobile app")
    Rel(cartculate, visionLlm, "Would send receipt images, receive structured item matches", "HTTPS (planned)")

    UpdateRelStyle(cartculate, visionLlm, $lineStyle="dashed")
Notes

There is exactly one first-class actor today: the household shopper. No multi-tenant/family-sharing concept exists yet.

The Vision/LLM Provider integration is drawn with a dashed relationship because it is planned but not implemented — the receipt scanner's OCR step currently operates against mock data; the confirm step's writes are real.

2. Container

The three deployable/runnable pieces and how they talk to each other.

C4Container
    title Cartculate — Container Diagram

    Person(shopper, "Household Shopper")

    System_Boundary(cartculate, "Cartculate") {
        Container(mobileApp, "Cartculate Mobile App", "React Native, TypeScript", "Cart, Recipes, Insights, and Receipt Scanner screens")
        Container(api, "Cartculate API", "Java 25, Spring Boot 4.1", "REST API: cart, recipes, purchase history, store pricing, user mode")
        ContainerDb(db, "Cartculate Database", "PostgreSQL 14", "Users, items, stores, prices, recipes, active cart, receipt history")
    }

    Rel(shopper, mobileApp, "Uses", "Touch")
    Rel(mobileApp, api, "Reads/writes cart, recipes, purchases, prices, mode", "HTTPS/JSON, REST")
    Rel(api, db, "Reads/writes via Spring Data JPA / Hibernate", "JDBC")
Notes

The mobile app holds no local persistence of its own — every screen fetches from the API on mount and calls it directly for every mutation. Optimistic UI updates exist for fast interactions (+/-, pantry, checkbox) with rollback-via-refetch on failure.

API_BASE_URL differs by platform during development (Android emulator needs 10.0.2.2 rather than localhost).

3. Component (backend)

Inside the Cartculate API container: controllers → services → repositories → JPA entities.

C4Component
    title Cartculate API — Component Diagram

    Container_Boundary(api, "Cartculate API") {
        Component(cartController, "CartController", "Spring RestController", "Cart CRUD, pantry-override, checkout-status, master-reset, complete-checkout")
        Component(recipeController, "RecipeController", "Spring RestController", "GET/POST recipes")
        Component(purchaseController, "PurchaseHistoryController", "Spring RestController", "GET/POST receipt-level purchase history")
        Component(storePriceController, "StorePriceController", "Spring RestController", "GET/PUT store prices")
        Component(userController, "UserController", "Spring RestController", "GET user, PATCH Home/Away mode")

        Component(cartService, "CartService", "Spring Service", "Cart consolidation, adjustment, pantry override, checkout toggle, trip completion")
        Component(recipeService, "RecipeService", "Spring Service", "Recipe CRUD, ingredient store-routing")
        Component(purchaseService, "PurchaseHistoryService", "Spring Service", "Archives receipts, serializes item manifest via Jackson 3")
        Component(storePriceService, "StorePriceService", "Spring Service", "Store price lookups and bulk upserts")
        Component(userService, "UserService", "Spring Service", "User profile + mode persistence")

        ComponentDb(repos, "Spring Data JPA Repositories", "8 repository interfaces", "User, Item, Store, StorePrice, Recipe, RecipeIngredient, UserCartItem, PurchaseHistory")
    }

    ContainerDb(db, "PostgreSQL", "Database")

    Rel(cartController, cartService, "calls")
    Rel(recipeController, recipeService, "calls")
    Rel(purchaseController, purchaseService, "calls")
    Rel(storePriceController, storePriceService, "calls")
    Rel(userController, userService, "calls")

    Rel(cartService, repos, "uses")
    Rel(recipeService, repos, "uses")
    Rel(purchaseService, repos, "uses")
    Rel(storePriceService, repos, "uses")
    Rel(userService, repos, "uses")

    Rel(repos, db, "JPA/Hibernate", "JDBC")
Notes

Every controller follows the same thin-controller/fat-service pattern: controllers only translate HTTP ↔ DTOs and delegate to a service.

DTOs are hand-written to mirror the frontend's TypeScript types field-for-field, avoiding a mapping/translation layer on either side.

RecipeService and CartService both depend on StorePriceRepository directly for read-side price lookups, rather than going through StorePriceService, since those are simple filtered reads rather than the bulk-upsert logic that service owns.
