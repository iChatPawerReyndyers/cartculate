Table-by-table notes

users

Single-tenant today. current_mode is a persisted HOME/AWAY toggle read/written by the Cart screen (GET/PATCH /api/users/{userId}/mode).

items

The master catalog. category (e.g. "Vegetables", "Meat", "Toiletries") drives the Insights tab's category-breakdown pie chart.

stores

Physical stores (Puregold, S&R in seed data).

store_prices

Composite key (item_id, store_id) — the same item can have a different price per store. Written to by manual price entry, the receipt scanner's confirm step, and read by cart consolidation, recipe ingredient store-routing, and reconciliation's expected-total calculation.

recipes / recipe_ingredients

recipe_ingredients uses a composite primary key (recipe_id, item_id) — a recipe can't list the same item twice. target_store_id is nullable: when set, that ingredient always routes to the specified store; when null, RecipeService falls back to whichever store currently has the cheapest known price for that item.

user_cart_item

The active cart. Each row represents one (item, store, source) line — source_recipe_id is nullable, and NULL specifically means "manually added, belongs to the Others bucket" rather than any particular recipe. See ADR-001 for why this table uses a surrogate id primary key instead of the fully-composite key its business logic implies.

override_pantry_qty / override_reason back Feature 5's Home Mode pantry-stock stepper; is_checked_checkout backs Feature 5's Away Mode checkbox and Feature 6's per-store "Done Checkout" reconciliation.

purchase_history

Receipt-level, not line-item-level: one row per checkout, with item_manifest_json holding a compressed snapshot of what was purchased. This is a deliberate tradeoff — see ADR-002.

Manifest shape (a JSON array):

[
  { "itemId": 6, "itemName": "Napkin", "category": "Toiletries", "quantity": 2, "pricePerUnit": 25.00 }
]

Known schema-modeling tradeoffs

Documented in more detail in the Decision Records, but worth flagging here since they directly affect how the ER diagram should be read:

  1. user_cart_item's intended business key (per the original product spec) was the composite (user_id, item_id, store_id, source_recipe_id) — but Postgres requires every PRIMARY KEY column to be NOT NULL, and source_recipe_id is nullable by design. The actual implementation uses a surrogate id PK plus a regular unique index on the same four columns (Postgres treats multiple NULLs as distinct in a unique index, unlike a primary key).
  2. purchase_history's item-level detail lives inside a JSON blob rather than a normalized child table, which trades query-ability (e.g. "sum quantity purchased of item X across all receipts" requires JSON parsing, not a GROUP BY) for a simpler write path at checkout time.
