Architecture Decision Records

Lightweight ADRs for decisions that weren't obvious from the spec alone, or that diverged from it for a concrete technical reason.

ADR-001: Surrogate primary key for user_cart_item

Context: The product spec's SQL defined user_cart_item's primary key as the composite (user_id, item_id, store_id, source_recipe_id), with source_recipe_id explicitly nullable to represent the "Others" bucket.

Problem: PostgreSQL requires every column in a PRIMARY KEY constraint to be NOT NULL. A literal implementation of the spec's key would reject every "Others" row (source_recipe_id IS NULL) outright.

Decision: Keep a surrogate id BIGINT primary key, and enforce the spec's intended business key as a regular unique index instead: UNIQUE (user_id, item_id, store_id, source_recipe_id).

Consequence: Postgres treats multiple NULLs as distinct under a unique index (unlike a primary key), so this preserves the one-row-per-(item, store, recipe) semantics the spec intended, without breaking on the "Others" case.

ADR-002: purchase_history moved to receipt-level with a JSON manifest

Context: An early version of the schema had one row per item purchased. A later spec revision changed this to one row per receipt, with a manually-entered total and a JSON snapshot of the cart.

Decision: Adopted the receipt-level model, storing the manifest as a native jsonb column.

Consequences:

  • Simpler write path: one INSERT per checkout instead of N.
  • Simpler variance detection: reconciliation naturally compares one expected total against one actual total.
  • Weaker query-ability: per-item analytics now require parsing the JSON manifest client-side rather than a simple GROUP BY item_id — an accepted tradeoff, not an oversight.
  • Postgres requires an explicit ::jsonb cast when inserting a text value built via || concatenation — the "unknown" literal type Postgres can implicitly cast only applies to bare string literals.

ADR-003: Jackson 3, not Jackson 2

Context: PurchaseHistoryService needs to serialize a structured item list into JSON. Injecting Jackson's ObjectMapper failed to compile with package com.fasterxml.jackson.databind does not exist.

Decision: Spring Boot 4 defaults to Jackson 3, whose classes live under tools.jackson.databind, with JsonMapper replacing ObjectMapper as the auto-configured bean type. Jackson 2 is not on the classpath by default. PurchaseHistoryService injects tools.jackson.databind.json.JsonMapper instead.

Consequence: No pom.xml change was needed — spring-boot-starter-web already pulls in Jackson 3 via spring-boot-starter-json. Any future JSON handling in this codebase should use the Jackson 3 types, not assume Jackson 2 APIs from older references.

ADR-004: ddl-auto=update requires a database reset after certain schema changes

Context: Several schema changes (new required columns on recipes, users, purchase_history) caused startup failures: ERROR: column "X" of relation "Y" contains null values.

Root cause: Hibernate's ddl-auto=update can only add schema — it cannot safely backfill a NOT NULL column being added to a table that already has existing rows.

Decision: No code-level fix applies (it's an inherent limitation of update mode). The operational answer: when a schema change adds a required column and local dev data already exists, drop and recreate the database before the next run, letting Hibernate build the schema fresh and data.sql's empty-table guard reseed it automatically.

Consequence: Acceptable for a pre-production system with disposable seed data. Would not be acceptable once real user data exists — at that point, ddl-auto should move to validate and real migration tooling (Flyway/Liquibase) should own schema changes.

ADR-005: Home/Away mode is persisted server-side

Context: Feature 5's Home/Away toggle could have been simple local component state, reset on every app restart.

Decision: Persist the mode on the User entity (current_mode VARCHAR(10)), with GET/PATCH /api/users/{userId}/mode endpoints, so it survives restarts and (eventually) syncs across devices.

Consequence: CartScreen fetches the mode on mount and calls the update endpoint optimistically, the same pattern used elsewhere for cart mutations.

ADR-006: category threaded through DTOs after the fact

Context: Feature 6's reconciliation flow needed each cart item's category to build the purchase manifest — but CartRowDto and RecipeIngredientDto didn't originally expose it, even though Item always had the column.

Decision: Added category to both DTOs and their frontend TypeScript counterparts, threading it through every function that constructs these objects.

Consequence: No database migration was required — unlike ADR-004's scenario, category already existed as a column; this was purely a DTO/type-surface gap.

ADR-007: Client-side regex sanitization enforces decimal precision, not just server-side column types

Context: Quantities and prices are stored as NUMERIC(10,2)/NUMERIC(10,3) in Postgres, but nothing stopped a user from typing something like 12.4567 or 12..3 into a free-text field (the reconciliation screen's actual receipt total, new-recipe ingredient quantities) before it ever reached the backend.

Decision: Added src/utils/inputSanitization.ts on the frontend: sanitizeDecimalInput() strips invalid characters and caps decimal places as-you-type (on every onChangeText, not just on submit), sanitizeIntegerInput() does the same for whole-number-only fields (discrete pc/pack quantities), and a shared formatCurrency() replaced scattered .toFixed(2) calls across components for consistent display.

Consequence: Invalid characters never appear in the field at all, rather than being caught only at validation time - a stricter guarantee than server-side type coercion alone, and it also means the same 2-decimal-place rule can't drift between different components' .toFixed() calls, since they all defer to the one shared function now.

ADR-008: Per-source pantry/checkout controls moved into the accordion breakdown

Context: When an item was split across multiple recipe sources (e.g. Carrots needed by both Caldereta and Giniling), the Home Mode pantry-override stepper and Away Mode checkout checkbox only ever targeted one underlying row (primaryRowId - the manual "Others" row if one existed, otherwise whichever source arrived first). There was no way to mark just the Caldereta-sourced carrots as already-home while leaving the Giniling-sourced ones untouched.

Decision: Added per-source overridePantryQty, overrideReason, and isCheckedCheckout fields directly onto each BreakdownEntry (not just the item-level aggregate), and moved the actual stepper/checkbox controls into each expanded accordion row for multi-source items. Single-source items are unaffected - they still show one item-level control below the main row via primaryRowId, since there's nothing to disambiguate.

Consequence: cartLogic.consolidateCart() now populates these fields per breakdown entry during aggregation. No backend or database change was needed - the underlying user_cart_item rows already carried per-row pantry/checkout state; this was purely a frontend gap in how that state was surfaced.
